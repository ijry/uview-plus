# Dragsort 小程序句柄与内容包装层修复设计

## 背景

`u-dragsort` 修复微信小程序拖动松手覆盖后，仍有两个跨端表现问题：微信小程序中自定义 `handler` 具名插槽不显示；横向和多行多列模式中，项目右侧出现额外白色区域。

## 根因

- 微信小程序编译后的具名插槽可能通过 `$slots.$handler` 暴露，组件需要同时兼容两种插槽标识。
- `handler` 出口位于 `v-for` 内并传递 `item/index`，微信小程序会将其编译为 `handler-0`、`handler-1` 等动态作用域插槽。调用方若只写 `<template #handler>`，产物只提供静态 `slot="handler"`，无法与循环内动态出口匹配，因此节点虽然存在于父组件 WXML 中，却不会显示在子组件内。
- `.u-dragsort-item-content` 同时承担尺寸测量和视觉卡片样式。其背景、边框和圆角会覆盖调用方为项目间距预留的 padding，因此横向和网格项目尾部出现白色块。

## 方案

1. 新增 `hasHandler` 计算属性，同时兼容 `$slots.handler` 与 `$slots.$handler`。
2. 模板中的句柄显示和 `onTouchStart` 的触摸限制统一使用 `hasHandler`，避免显示条件与交互条件不一致。
3. 示例调用显式声明 `#handler="{ item, index }"`，让微信编译器为每个拖动项生成与组件动态出口匹配的句柄插槽。
4. 保留 `.u-dragsort-item-content` 的定位、padding 和盒模型，只移除背景、边框和圆角，使其恢复为纯结构与尺寸测量容器。
5. 扩展现有静态回归脚本，覆盖小程序插槽别名、作用域句柄写法和包装层不强制卡片样式三项约束。

## 兼容性

- H5 原有 `$slots.handler` 行为不变。
- 微信小程序通过 `$slots.$handler` 正常识别自定义句柄，并通过作用域插槽为每个列表项生成独立句柄节点。
- 默认插槽内容的视觉样式改由调用方控制，与组件早期结构层行为一致。
- 拖动排序数据、事件和三种方向模式的定位逻辑不变。

## 验证

- 先扩展 `npm run verify:dragsort-stable-identity`，确认现有实现无法满足新增约束。
- 实现后重新运行专项校验。
- 执行 `npm run build:mp-weixin`，确认微信小程序模板和样式编译成功。
- 检查编译产物，确认句柄条件包含小程序插槽映射，内容包装层不再输出卡片背景和边框。
