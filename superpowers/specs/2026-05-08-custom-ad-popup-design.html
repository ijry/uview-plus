# Custom Ad Popup Design

# Scope

Upgrade only the ad popup component in docs/.vuepress/theme/components/adVip.vue.

The change keeps the existing backend API contract, local cache keys, 12-hour ad-free window, route whitelist, and page mounting behavior. It does not change membership verification, ad verification endpoints, site navigation, or non-ad Element UI usages elsewhere in the docs site.

# Current State

The ad popup is mounted from docs/.vuepress/theme/components/Page.vue through <ad-vip>. The component currently uses Element UI for the modal, loading state, buttons, and message prompts. Its anti-tamper checks look for Element UI DOM classes such as .v-modal and .el-dialog__wrapper.

That creates predictable selectors. A blocking rule can hide or remove those classes without understanding the component.

# Recommended Approach

Replace the Element UI modal inside adVip.vue with a fully custom Vue template:

  • A custom overlay node.
  • A custom panel node.
  • Native buttons and links.
  • An internal loading placeholder for the QR code.
  • Inline success and error messages instead of $message.

The popup will generate runtime identifiers for its overlay and panel, including dynamic id values and data-* guard markers. The implementation will avoid stable Element modal class names and avoid relying on Element UI DOM structure.

# Behavior

The existing user-facing flow remains the same:

  1. Route changes call checkVip.
  2. Whitelisted routes hide the popup.
  3. Non-whitelisted routes read localStorage.adExpire3.
  4. Expired or missing access calls plsdontcrack.
  5. The component calls https://uiadmin.net/api/v1/wxapp/ad/add.
  6. If the backend reports valid access, the popup closes and stores a new 12-hour adExpire3.
  7. Otherwise, the QR code is shown.
  8. "已经看完" calls https://uiadmin.net/api/v1/wxapp/ad/check?id=....

# Anti-Tamper Guard

The guard starts only while the popup is required and visible. It stops when the popup is closed, the route is whitelisted, or verification succeeds.

The guard checks:

  • Overlay and panel nodes still exist.
  • Nodes still contain the expected runtime token.
  • Computed display, visibility, opacity, and pointer-events allow interaction.
  • Rect dimensions are non-zero.
  • Position and z-index keep the popup visible above the page.
  • The panel has not been moved far outside the viewport.

For light tampering, the component restores critical inline styles on the overlay and panel. For repeated or unrecoverable tampering, it enters a blocked state and shows a clear support message through the custom popup surface.

# Component State

Keep existing state that affects behavior:

  • id
  • qrDialog
  • qrUrl
  • watchEnd
  • timer
  • check
  • whiteList

Add implementation state:

  • guardToken
  • overlayId
  • panelId
  • guardObserver
  • guardFailures
  • notice
  • noticeType
  • isLoadingQr
  • isCheckingEnd
  • isBlocked

# Error Handling

Network or API failures are shown inside the custom popup using a local notice area.

The component should not use blocking browser alert loops during normal recovery. A hard page opacity fallback may remain only for unrecoverable repeated tampering, but it should not trigger for ordinary API failures or slow QR loading.

# Styling

The modal must be usable on desktop and mobile:

  • Fixed full-screen overlay.
  • Centered panel with responsive width.
  • Scrollable panel body on small screens.
  • QR image constrained to the panel width.
  • Clearly styled primary action and secondary login link.
  • No dependency on Element UI modal, loading, or button classes.

# Testing

Manual and automated checks should cover:

  • Build succeeds.
  • Popup renders on non-whitelisted routes when adExpire3 is missing or expired.
  • Popup does not render on whitelisted routes.
  • QR loading state displays before qrUrl is available.
  • Success response closes the popup and stores adExpire3.
  • Failed check displays an inline error.
  • Hiding/removing the custom overlay or panel is detected and recovered or blocked.
